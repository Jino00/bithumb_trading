## 2. 전략의 코인/레짐 종속성 — 범용 전략은 없다

### 🐛 이슈
모든 전략을 모든 코인+레짐에 동일하게 적용하면 전체 합산 성과가 대폭 악화.

- S4: ETH에서만 안정적 (DOGE 33.3%, BTC 42.9%이나 PF 0.93)

### ✅ 해결

### 📌 교훈
- **"하나의 전략으로 모든 코인"은 환상** — 반드시 코인별 최적 전략 매핑 필요
- 새 전략 추가 시 반드시 **코인별 × 레짐별 성과 매트릭스** 확인 후 배정

## 4. macOS SSL 인증서 — WebSocket 연결 실패

### 🐛 이슈
빗썸 WebSocket(`wss://pubwss.bithumb.com/pub/ws`)에 `websockets.connect()` 시
`SSL: CERTIFICATE_VERIFY_FAILED` 오류로 연결 실패. macOS의 system Python이
시스템 인증서를 자동으로 찾지 못하는 문제.

### ✅ 해결
- `ssl.create_default_context()`에 `certifi.where()`로 인증서 경로 명시
- certifi 없을 경우 `load_default_certs()` → 그래도 실패 시 `CERT_NONE` 폴백

### 📌 교훈
- **macOS + Python에서 SSL 연결 시 항상 certifi 사용** — 기본 인증서 경로를 못 찾는 경우가 많음
- `pip install certifi`가 되어 있어도 `ssl` 모듈이 자동으로 참조하지 않음
- WebSocket, requests 등 SSL 연결 코드에서는 항상 certifi 호환 처리 필요

## 5. 롤링 평균 기반 고래 감지 — 윈도우에 고래 거래 포함 시 평균 왜곡

### 🐛 이슈
고래 거래를 롤링 윈도우(deque maxlen=200)에 추가하면, 해당 대형 거래가 평균을 끌어올려
배율(size_ratio)이 낮아지는 문제. 예: 20건×50만 + 1건×300만 → 평균 62만 → 배율 4.8x (5.0 미달).

### ✅ 해결
- 테스트에서 윈도우를 충분히 채운 후(200건) 고래 거래 주입으로 평균 왜곡 최소화
- 실전에서는 200건 윈도우로 1건의 대형 거래 영향이 0.5%로 미미

### 📌 교훈
- **롤링 평균 기반 이상치 감지 시 윈도우 크기가 핵심** — 너무 작으면 대형 거래가 평균을 왜곡
- 테스트 작성 시 윈도우를 충분히 채운 상태에서 검증해야 정확

## 6. 실시간 감지와 실시간 거래는 별개 — 콜백과 액션의 분리

### 🐛 이슈
WebSocket으로 고래를 실시간 감지하도록 구현했지만, 콜백(`_on_whale_alert`)이
화면 출력만 수행. 트레이딩은 여전히 1분 스케줄러(`schedule.every(1).minutes`)로만 실행.
**실시간 감지 ≠ 실시간 거래** — 감지 파이프라인과 실행 파이프라인이 연결되어야 함.

### ✅ 해결
- 콜백에서 해당 코인의 `trading_cycle()`을 즉시 호출
- `whale_buy_boost` 플래그로 전략 BUY 신호 시 즉시 진입
- 전략 신호가 없으면 고래 매수만으로는 진입하지 않음 (안전장치)

### 📌 교훈
- **데이터 수신과 행동 실행을 항상 같이 설계할 것** — 수신만 빠르고 행동이 느리면 의미 없음
- 콜백 기반 즉시 실행 시 **일일 가드/포지션 보유** 등 안전장치 반드시 포함
- 고래 신호는 전략 신호의 **부스터**지, 독립적인 매매 신호가 아님

## 7. 스크리너-고래 충돌 — 두 코인 선별 시스템의 권한 경쟁

### 🐛 이슈
코인 스크리너(거래대금+변동폭 기반, 5분마다)와 고래 감지기(WebSocket 실시간)가 동시에
코인 추가/제거를 결정하면서 13가지 충돌이 발생:

1. **쓰레드 안전 위반**: 고래 콜백(WebSocket 쓰레드)이 메인 루프의 slots/bench를 락 없이 수정
2. **드레인 vs 매수 레이스**: 스크리너가 드레인 설정 직후 고래가 trading_cycle 호출
3. **선별 기준 불일치**: 스크리너는 변동폭 2%+ 필터, 고래는 매수압력만 봄
4. **블랙리스트 충돌**: 고래가 BULLISH인데 블랙리스트라서 묵살됨
5. **벤치 순회 중 변경**: 고래가 벤치에 추가하는 동안 스크리너가 벤치 순회
6. **명령 충돌**: 스크리너 "제거" vs 고래 "유지" → 항상 스크리너 승리

### ✅ 해결
**고래 우선 원칙** 적용:
- `threading.Lock()`으로 slots/bench 접근 동기화
- 고래 매수 감지 코인에 30분 "보호" 플래그 → 스크리너 드레인/벤치 제거 유예
- 고래 BULLISH 코인은 블랙리스트 자동 해제
- 고래 매수 감지 시 드레인 중인 슬롯도 드레인 취소
- 인텔리전스 SELL 시그널에서도 고래 보호 코인은 드레인 유예

### 📌 교훈
- **두 개의 독립적인 코인 선별 시스템을 운용하면 반드시 권한 우선순위를 정해야 한다**
- 실시간 데이터(고래) > 정기 스캔(스크리너) — 실시간이 더 신선한 정보
- WebSocket 콜백은 반드시 쓰레드 락으로 보호해야 한다 — 레이스 컨디션은 디버깅이 극도로 어려움
- 보호 플래그에는 반드시 TTL(30분)을 두어야 한다 — 무기한 보호는 좀비 슬롯을 만듦

## 8. 외부 시장 트렌드 학습 — LLM + 웹 검색으로 전략 자동 조정

### 🐛 이슈
전략 파라미터(SL/TP/RR/ATR)가 초기 백테스트 최적값으로 고정되어 있어,
시장 환경이 변하면 성과가 하락한다. 수동으로 파라미터를 조정하려면
트레이더가 매주 시장을 분석해야 하는데 자동화 필요.

### ✅ 해결
- Gemini API + Google Search grounding으로 **매주 월요일 03:00** 자동 시장 조사
- 성공한 트레이더들의 매매 방식, 인기 지표, SL/TP 설정 등을 분석
- JSON 구조로 파라미터 제안 → 안전 범위 내 자동 적용 (SL 1~5%, TP 1.5~10%, RR 1.5~5.0)
- 신뢰도 30% 미만이면 적용 스킵 (안전장치)
- 주간 리포트 `.claude/memory/weekly_reports/`에 자동 저장

### 📌 교훈
- **LLM의 웹 검색 능력을 전략 파라미터 자동 튜닝에 활용할 수 있다**
- 반드시 **안전 범위**를 설정해야 한다 — LLM이 극단적 값을 제안할 수 있음
- 신뢰도(confidence) 필터가 핵심 — 낮은 신뢰도 제안은 오히려 해로움
- JSON 파싱 실패에 대한 폴백 필수 — LLM 출력은 항상 불안정할 수 있음

## 9. 쓰레드 안전 — 공유 상태 접근은 "기본이 락"이어야 한다

### 🐛 이슈
`_slots`와 `_bench` 딕셔너리를 6개 이상의 메서드에서 수정하는데, 고래 콜백(WebSocket 쓰레드)과
메인 스케줄러 쓰레드가 동시에 접근. 감사(audit) 결과 5곳에서 락 없이 접근하고 있었음:
- `_scan_and_update()` 내부 전체 (드레인, 벤치 업데이트, 승격, 교체)
- `_try_swap_weakest()` (슬롯 삭제)
- `_try_activate()` / `_try_activate_fixed()` (슬롯 추가)
- `_apply_intel_to_strategy()` (슬롯 순회 + 드레인)
- `_drain_coin()` (슬롯 삭제)

### ✅ 해결
- `_on_whale_alert()` (고래 쓰레드) → `with self._slot_lock` 적용
- `_safe_all_cycles()` (트레이딩 사이클) → `with self._slot_lock` 적용
- `_scan_and_update()` 내부 슬롯/벤치 변경 블록 → `with self._slot_lock` 적용
- `_apply_intel_to_strategy()` → 락 내부 메서드로 분리

### 📌 교훈
- **공유 상태를 수정하는 모든 메서드는 "기본이 락"이어야 한다** — 락 없이 접근하는 것이 예외
- 새 기능을 추가할 때 `self._slots`나 `self._bench`를 건드리면 → 반드시 `_slot_lock` 사용
- 메서드 이름이 다르면 같은 딕셔너리를 수정한다는 사실을 놓치기 쉬움 → **"_slots를 수정하는 메서드 목록"을 주석으로 관리**
- 스케줄러(schedule 라이브러리)는 단일 쓰레드지만, WebSocket 콜백은 별도 쓰레드이므로 항상 경계

## 10. 체계적 코드 감사 — 기능 추가 후 반드시 수행해야 할 점검 체크리스트

### 🐛 이슈
고래-스크리너 충돌 13개, 쓰레드 안전 갭 5개, `.all()` → `.all_coins()` 크리티컬 버그,
`whale_sell_alert` 데드코드, `avoid_strategies` 미연결 등이 전체 감사 전까지 발견되지 않음.
기능을 추가할 때마다 이런 감사를 수동으로 하면 놓치는 것이 필연적.

### ✅ 해결
다음 체크리스트를 기능 추가 후 반드시 수행:

1. **메서드 호출 체인**: 새로 만든 메서드가 실제로 호출되는지 (스케줄러 등록, 콜백 연결)
2. **API 일치**: 호출하는 메서드명/파라미터가 실제 정의와 일치하는지 (`.all()` vs `.all_coins()`)
3. **플래그 소비**: 새로 추가한 플래그(bool)가 설정(set)만 되고 읽기(check)는 안 되는지
4. **쓰레드 안전**: `_slots`, `_bench` 등 공유 상태를 건드리면 `_slot_lock` 안에 있는지
5. **충돌 분석**: 2개 이상의 시스템이 같은 자원을 제어하면 우선순위가 명확한지
6. **학습 출력 → 행동 연결**: 학습이 값을 생성하면 그 값이 실제 거래에 반영되는지
7. **안전 범위**: 외부 입력(LLM, API)이 전략 파라미터를 변경하면 범위 제한이 있는지

### 📌 교훈
- **기능 추가 후 "동작한다"와 "올바르게 연결되어 있다"는 다른 문제** — 테스트 통과 ≠ 시스템 정합성
- 체크리스트 없이 감사하면 반드시 빠지는 항목이 생김
- 특히 **플래그 설정만 하고 사용 안 하는 패턴**은 가장 흔한 미연결 버그

## 8. 급등락 코인 트레일링 스탑 — 티어별 최적 파라미터가 완전히 다름

### 🐛 이슈
급등락 코인에 일률적으로 트레일링 3%를 적용했더니, HOT(15~40%)급 코인에서 기존 전략 대비 -30.8% 악화.
반면 VOLATILE(8~15%)급에서는 +41.6%, EXTREME(40%+)에서는 +26.9% 개선.
하나의 파라미터로 모든 변동성 구간을 커버할 수 없음.

### ✅ 해결
6개월 43개 코인, 2371개 급등락일, 788건 거래로 540조합 그리드서치 수행.
티어별 최적 파라미터 발견:
- **VOLATILE(8~15%)**: 트레일링 2.5%, 활성화 1.0%, SL ×0.5, TP ×1.5 → PF 1.13
- **HOT(15~40%)**: 트레일링 4.0%, 활성화 0.5%, SL ×0.5, TP ×2.0 → PF 2.43
- **EXTREME(40%+)**: 트레일링 1.5%, 활성화 3.0%, SL ×0.5, TP ×1.0 → PF 3.26

### 📌 교훈
- **변동성 구간별로 최적 전략이 정반대** — HOT은 느슨한 트레일링(4%), EXTREME은 빡빡한(1.5%)
- HOT은 TP 2배 확대가 핵심 (큰 흐름을 타야 함), EXTREME은 TP 유지가 핵심 (욕심부리면 급락에 맞음)
- **공통**: SL ×0.5 (반으로 줄이기)가 모든 티어에서 최적 — 급등락 코인은 빠르게 손절해야 함
- HOT에서 트레일링이 -30.8% 악화한 이유: 기존 전략이 이미 PF 2.43으로 우수 → 트레일링이 수익 거래를 조기 청산

## 21. entry_time str→datetime 파싱 버그 — 타입 불일치 런타임 에러

### 🐛 이슈
`paper_trader.py`의 고래 매도 유예 기간 계산에서 `now - self._position.entry_time`을 수행하는데,
`entry_time`은 dataclass에서 `str` 타입으로 선언되어 있고(`"2026-03-15 12:08"` 형식),
`now`는 `datetime` 객체. `str - str`이 아닌 `datetime - str` 연산으로
`unsupported operand type(s) for -: 'str' and 'str'` 에러 발생.
해당 코인(SAHARA)의 트레이딩 사이클이 완전히 중단됨.

### ✅ 해결
```python
# 기존
hold_seconds = (now - self._position.entry_time).total_seconds()
# 수정
_et = self._position.entry_time
if isinstance(_et, str):
    _et = datetime.strptime(_et, "%Y-%m-%d %H:%M")
hold_seconds = (now - _et).total_seconds()
```

### 📌 교훈
- **dataclass 필드 타입과 실제 사용 시 기대 타입이 다를 수 있다** — `entry_time: str`인데 datetime 연산을 하면 런타임 에러
- 새 코드에서 기존 dataclass 필드를 사용할 때 **타입을 반드시 확인**하고, str이면 파싱 후 사용
- 이상적으로는 `entry_time`을 `datetime` 타입으로 변경하되, JSON 직렬화와의 호환성 때문에 str로 유지되는 경우가 많음
- **타입 힌트가 `str`인 필드에 datetime 연산을 직접 적용하지 말 것** — 항상 변환 래퍼 사용

## 22. 슬롯 교체 로직의 3가지 병목 — 과도하게 보수적인 설정

### 🐛 이슈
10개 활성 코인이 시간이 지나도 전혀 교체되지 않음. 원인 3가지:
1. **벤치 대기시간 15분** — 벤치에 추가된 코인이 승격 자격을 얻기까지 15분 대기 필요
2. **슬롯 체류시간 1시간** — 활성 슬롯이 교체 대상이 되려면 최소 1시간 유지 필요
3. **점수 비교 스케일 불일치** — `weakest_score`는 전략 평가 점수(10~50 범위), `bench_score`는 `range_pct`(변동폭 %). 전혀 다른 스케일을 직접 비교하여 교체 판단이 무의미

이 세 조건이 동시에 충족되는 순간이 극히 드물어 실질적으로 교체 불가.

### ✅ 해결
- `BENCH_MIN_WAIT_HOURS`: 0.25 → 0.02 (~1분)
- `ACTIVE_MIN_STAY_HOURS`: 1.0 → 0.083 (5분)
- `SWAP_SCORE_ADVANTAGE`: 1.2 → 1.1 (10% 우위)
- 점수 비교를 `_slot_effectiveness()` 함수로 통일 — 거래 실적(거래 수, 수익률) + 전략 점수 + 체류 페널티를 종합
- 디버그 로그 추가로 비교 과정 투명화

### 📌 교훈
- **설정값은 "안전하게 크게"가 아니라 "실제 시장 속도에 맞게"** — 1시간 체류는 5분봉 코인에겐 과도
- **서로 다른 스케일의 점수를 직접 비교하면 안 된다** — 반드시 정규화하거나 동일 기준으로 환산
- 교체 로직에 **디버그 로그가 없으면 병목을 찾을 수 없다** — "왜 교체가 안 되지?"를 답하려면 매 비교 결과를 출력해야 함
- 보수적 설정 → 로그 없음 → 문제 모름 → 설정 더 보수적으로 → 악순환

## 23. 비존재 속성 참조 — 새 코드에서 기존 클래스 속성 미확인

## 38. 매도 시 잔액 덮어쓰기 버그 — `balance = returned_krw`

### 🐛 이슈
`paper_trader.py:591` — 매도 시 `self._balance_krw = returned_krw`로 잔액을 반환금으로 **교체**함.
매수 시에는 `balance -= invest_krw`로 투자금만 차감하므로, 미투자 잔금이 남아있음.
매도 시 반환금으로 덮어쓰면 미투자 잔금이 증발함.

예: 배분금 973,038원 중 500,000원 투자 → 잔금 473,038원 남음.
매도 시 반환금 495,018원 → `balance = 495,018` (473,038원 증발!)
결과: ETH -50.51% (-491,502원) 표시 — 실제 거래 손실은 -1.02% (-4,982원)이었음.

### ✅ 해결
`self._balance_krw = returned_krw` → `self._balance_krw += returned_krw`

### 📌 교훈
- `=`와 `+=`의 차이가 -50% 손실을 만듦 — 재무 관련 변수는 항상 `+=`, `-=`만 사용하고, 직접 대입은 초기화 시에만
- paper trading 잔액 변동은 매 거래 후 검증 로직 추가 필요 (잔액 > 0 & 잔액 <= 배분금)
- 거래 1건의 인사이트 손실(-4,982원)과 실제 잔액 손실(-491,502원)이 다르면 즉시 의심해야 함

## 38. rebalance_allocations() 잔액 덮어쓰기 — ETH -50.51% 유령 손실

### 🐛 이슈
ETH 슬롯이 allocated_krw=973,038 → balance_krw=481,536 (-491,502원, -50.51%) 기록.


## 39. 거래 0건 — 전략 선택 과도 차단으로 학습 불가 악순환

### 🐛 이슈
10개 슬롯 전부 HOLD 상태, 거래 0건. 원인 3중 차단:
1. `strategy_evaluator.py`: `scores[0].score > 0` → 모든 전략 점수가 마이너스면 선택 불가
2. `scalp_strategy.py`: EMA200 필터가 SIDEWAYS에서도 적용 → 진입 기회 과도 차단
3. HOLD 모드 fallback 없음 → 전략 없으면 아예 거래 안 함

결과: 거래 0 → 학습 데이터 0 → 인사이트 0 → 개선 불가 → 계속 거래 0 (악순환)

### ✅ 해결
1. 전략 선택 임계치: `score > 0` → `score > -5` (학습 위해 거래 기회 확보)
2. EMA200 필터: BULL에서만 적용, SIDEWAYS는 통과 (레인지 바운스 허용)
3. Fallback 전략: 양호한 전략 없어도 최고 점수 전략을 활성화

### 📌 교훈
- **거래가 없으면 학습도 없다** — 대원칙 "이익의 최대화"를 위해선 먼저 거래가 일어나야 함
- 보수적 필터의 누적 효과를 주의: 개별 필터는 합리적이어도, 3중 필터가 동시 적용되면 거래 기회가 0에 수렴
- Paper trading은 실험 목적 — 손실 두려워하지 말고 다양한 거래를 해서 학습 데이터를 축적해야 함
